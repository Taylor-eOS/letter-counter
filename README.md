This is a character-level compression scheme designed for short chat messages on constrained hardware, where the encoder and the input keyboard are the same object. English text, especially informal chat text, is highly predictable at the character level. Given the character you just typed, the next character is almost never drawn from the full alphabet, it comes from a small set of likely followers.<br>
The system encodes each character as a 3-bit code whose meaning depends entirely on the previous character. There is no global symbol table. A 3-bit code means whatever the current context says it means. Encoder and decoder share an identical table, a 2D array of roughly 29 rows by 8 columns, where each row corresponds to a context character and each column corresponds to one of the 8 most probable followers of that character in the target corpus. The table fits in under 250 bytes and never changes at runtime.<br>
The alphabet is reduced to approximately 22 letters by treating visually similar pairs as identical, l and 1, case folded to lowercase throughout, and dropping extremely rare letters like q and x entirely, substituting k and ks at the keyboard level. This reduction costs almost nothing in chat text readability and means the 8-slot rows cover a higher fraction of what users actually type.<br>
Space is not treated as a context character because it is informationally empty, it carries no prediction about what follows beyond "a new word is starting." Instead, space transitions the context to a dedicated WORD_START state which has its own row in the table, trained on word-initial letter frequencies. The most common word starters in English chat text, roughly t, a, s, h, w, i, o, b, fill those 8 slots. Space itself occupies one code slot in every other context row as a valid next character, but it is a transition trigger rather than a content symbol.<br>
The keyboard is the encoder. At any moment the keyboard displays exactly the 8 characters available in the current context. The user cannot type outside the table because those keys do not exist in that moment. There are no escape codes, no fallback sequences, no variable-length exceptions. Every character transmitted is exactly 3 bits. A 20-character message is 60 bits, 8 bytes. The decoder on the receiving end maintains the same context state, does one table lookup per 3-bit code, and emits the corresponding character. It requires no heap allocation, no library, and no state beyond the current context index.<br>
The compression ratio on chat text is approximately 3 bits per character against ASCII's 8, giving roughly 2.5× size reduction. Unlike general-purpose compressors, this ratio is consistent across very short messages because there is zero framing overhead, the first character is already compressed, and a 4-character message compresses as efficiently as a 40-character one. Systems like Unishox2 achieve better ratios on long formal English but carry framing and mode-switching overhead that makes them less efficient than raw ASCII on the short informal fragments that dominate chat.<br>
The table is trained once on a representative corpus of chat messages. Training is straightforward: for each character in the corpus, record what follows it, count frequencies per context, and take the top 8 per row. The resulting table is a static constant in firmware. Updating it means recompiling, which is appropriate for a purpose-built communication system where both ends are under your control.
